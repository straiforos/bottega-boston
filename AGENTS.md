# App architecture

- Compose the single-page restaurant experience at the index route using the attached Bottega components and canonical CSS; preserve the library-owned appearance.
- Keep original uploaded and downloaded media in CDN pointer imports; do not embed raw binary copies in app source.
- Keep offering cards aligned and animate their wrappers with scroll-linked sequential reveals inside a pinned (sticky) track on desktop so the section holds until all cards land; rise and fall track scroll position and reverse; preserve library component appearance and respect reduced motion so updates remain compatible and content stays accessible.
- Use a wrapper layout for the overlapping club ribbon; library components retain their own appearance so design-system updates remain compatible.
- Compose alternating sketch separators around the library marquee and keep the home menu introduction inside the pinned offerings section to avoid duplicate section headings.
- Keep the real menu in a dedicated /menu route with source-derived structured data and individual illustrative image imports; home menu actions use a TanStack createLink wrapper around LinkAction without editing vendor components.
- Compose both page headers through BottegaHeader using the library's separate mark and wordmark variants and router-aware LinkAction navigation so branding and navigation remain consistent.
- Render the shared footer once from the `_site` pathless layout route (`src/routes/_site.tsx`) so every guest page gets the same footer automatically; pages never compose SiteFooter themselves.
- Mark up footer contact details (locations, email, phone, social link) with HTML5 address elements and reset their UA italic in the footer style layer so contact info stays semantic and legible.
- Give every gallery media a Bottega tomato hairline with hover zoom and a light overlay mask, and drive the gallery video with the same custom play control pattern as the story video (never native controls); respect reduced motion.
- "Order now" scrolls to #locations; staff edits https URLs in home_content. BottegaMap pins and inset address/order cards keep locations crawlable and library-styled.
- Keep route modules declarative and thin; compose page sections from `src/features`, reusable interface pieces from `src/components`, behavior from hooks or pure helpers, and English copy from `src/content/en` so future localization does not require presentation edits.
- Style via shared/home/menu stylesheets with Bottega tokens only; test filtering, scroll math, metadata, a11y in Vitest.
- Menu content lives in public menu_sections/menu_items, read client-side with bundled menu-data.ts as SSR fallback; inline editing on /menu only, RLS `has_role admin` as the sole write gate; the filter follows the URL hash (`selectionForMenuHash`), applied after hydration, a rail click outranking it.
- Staff access is Google sign-in restricted by public.staff_allowlist (signup blocked by an auth.users trigger; admin role granted by trigger) — why: no self sign-up, roles never derived from client data.
- Gallery tiles live in gallery_items (seeded rows reference bundled CDN assets by asset_key) and are edited inline on the home page by staff — why: same single-page, RLS-gated admin pattern as the menu.
- Gallery staff actions overlay fixed-aspect media, the add action occupies the final scroll slot, and full forms open in accessible dialogs — why: editing must not change the gallery height or surrounding page spacing.
- Media processing runs in the staff browser: photos in a module Web Worker (OffscreenCanvas), videos in ffmpeg.wasm loaded lazily from staff editors only — why: the Worker server can't run sharp/FFmpeg, and visitors must never download the tooling.
- Draw app-owned inline icons as SVG with `currentColor`, no width/height or transform attributes — each direction its own path geometry, sized by a shared-stylesheet class from `--bt-icon-size` — why: the library does this, so icons inherit themed ink on its scale.
- Pasta Club email architecture rules live in `src/lib/email/AGENTS.md`.
- Hero, ribbon and the three fixed offering cards read from public.home_content (keyed jsonb, admin-only writes) merged over bundled defaults in `src/lib/home/home-content.ts`, edited inline via floating staff buttons + dialogs — why: same single-page RLS-gated admin pattern; card ink is derived from the chosen surface so staff can't pick illegible pairings.
- Subdirectories may have their own `AGENTS.md`; read it before changing files there.
- Events (one-off and repeating, expanded by the pure `src/lib/events/occurrences.ts` in the event's time zone) are edited client-side under admin RLS; catering/event-space requests are written only through the public `submitRequest` server function, which re-prices order lines from the catering menu and rate-limits by email — why: the request table has no public insert, so the server is the only intake boundary.
